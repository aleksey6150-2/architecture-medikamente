# Решение заданий спринта 10

## Задание 1

Главная находка по As-Is — данные лежат вплотную к пользователям и защищены только доменной аутентификацией: нет шифрования, нет аудита, нет разграничения доступа. Самое острое — ПДн (ФИО пациентов и врачей) торчат прямо в именах файлов и папок (Pacient1-FIO-BD, Journal-Doctor-FIO), то есть утекают ещё до открытия файла. Категории данных не разделены — медицинские, финансовые и административные свалены на одном диске, а ресепшен по факту суперюзер с доступом к медкартам. Privacy by Design отсутствует, минимизация нарушена (избыточные поля, дубли Excel+1С, бэкапы, выгрузки аналитика на сырых ПДн), Data Lineage и реестра обработки нет вообще. По CIA проседают все три плеча. Ключевой приём, который примиряет цель «копить данные для ML» с минимизацией: операционный контур работает с зашифрованными/псевдонимизированными данными, аналитический (ClickHouse) — только с обезличенными.

Data flow diagram построены по четырём процессам: запись на приём, ведение медкарты, обработка анализов, приём и процессинг платежей. В target-версии на тех же потоках показаны шифрование и теги на хранилищах, AuthZ и аудит на процессах, TLS и минимизация на входах, обезличивание на потоке в аналитику и границы доверия.

## Задание 2

Ключевая идея по Privacy by Design — приватность не точечная, а сквозной слой платформенных блоков (на диаграмме выделены зелёным): API Gateway, IAM, PDP/ABAC на OPA, сервис согласий, каталог с тегами и lineage, Vault, сервис маскирования, DLP, сервис жизненного цикла и аудит. Каждый прикладной сервис обязан пройти через IAM (кто) и ABAC по тегам (что можно), взять ключи из Vault, отдать данные через маскирование и записать доступ к Restricted в аудит — так ни один функциональный блок не работает с ПДн в обход политик

### Новые блоки Privacy by Design
API Gateway · IAM · PDP/ABAC (OPA) · Сервис управления согласиями · Каталог + Lineage + Тегирование · Vault/KMS · Сервис маскирования/обезличивания · DLP · Сервис жизненного цикла (Retention) · Аудит и мониторинг · Операционная БД с доменами.

### Аналитический слой
Отдельный контур: ETL с обезличиванием на загрузке → ClickHouse (только обезличенные данные) → BI/ML/Jupyter. Идентифицирующие данные не покидают операционный контур (принцип положительной суммы).

### Принципы
Privacy by Design (7 принципов) · Data Minimization · Data Lineage · 152-ФЗ · локализация данных в РФ.

## Задание 3

Оценка шифрования данных в режиме "данные лежат" и "данные передаются"

Классификация данных (по состоянию, чувствительности, профилю риска); обоснование необходимости защиты и инструменты (таблица в формате задания); стратегии шифрования at-rest и in-transit; автоматизированный контроль; **реестр программных и аппаратных средств**
Документ приведен здесь: [README_task3.md](Task3/README_task3.md)

### Структура документа
1. Модель классификации по нескольким параметрам (состояние / уровень / категория / профиль риска).
2. Сводная классификация данных и методы защиты по состояниям.
3. **Таблица «Данные → необходимость защиты → инструменты»** (требуемый формат).
4. Базовые средства at-rest (диск, БД, поля, объекты, бэкапы, управление ключами, ГОСТ-СКЗИ).
5. Базовые средства in-transit (TLS 1.3, mTLS, ГОСТ-VPN между филиалами, почта, сертификаты).
6. Автоматизированный контроль (OPA, CI-гейты, TLS/cert-мониторинг, DLP, SIEM, алертинг).
7. **Реестр ПО и АО** с пометкой «базовое / добавить».
8. Соответствие 152-ФЗ, ПП-1119, ФСТЭК/ФСБ, ГОСТ; закрытие проблем P-02/P-03 и др. из Task 1.

### Ключевые акценты
- Шифрование как **слои**: диск → том → поле → канал → ключи.
- Для спец. категории ПДн — сертифицированные **ГОСТ-СКЗИ** (CryptoPro / ViPNet); уровень защищённости ИСПДн по ПП-1119.
- С открытием филиалов — **аппаратные криптошлюзы** (ГОСТ site-to-site VPN) и HSM/токены.
- Большая часть базовых средств уже есть в стеке (Vault, PostgreSQL, ClickHouse, Elastic, Victoria Metrics, Kubernetes).

## Задание 5 Разработка cutover-плана

### Выбранная стратегия
**Parallel run** — старая и новая системы работают параллельно, legacy остаётся источником истины, нагрузка переводится постепенно (canary по процессам/филиалам), откат малозатратен. Обоснование выбора и сравнение с High-level design и Branch by abstraction — в документе.

### Структура cutover-плана
Подготовка → Тестирование → Параллельный запуск (shadow) → Постепенный перевод нагрузки → Ворота Go/No-Go → Полный cutover → Hypercare → Декомиссия. План отката доступен на всём пути.

### Ключевой риск
Синхронизация данных между системами → dual-write/CDC + ежедневная автоматическая сверка с журналом расхождений и порогами.
