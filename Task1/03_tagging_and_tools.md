# Механизм тегирования данных и инструменты защиты
*Task 1 — обеспечение конфиденциальности в потоках данных*

## Часть A. Механизм тегирования данных

### A.1 Принципы
1. **Тег ставится у источника** (в момент создания/приёма данных) и далее **наследуется по графу происхождения (Data Lineage)** — любой производный набор данных получает теги родителя.
2. **Теги управляют политиками** (tag-driven): доступ (ABAC), маскирование, срок хранения, разрешённые среды и проверка релизов опираются на теги, а не на ручные правила.
3. **Новые интеграции не требуют ревалидации**: если данные уже размечены, политики применяются автоматически (требование из целей бизнеса).

### A.2 Модель тега
Тег = **уровень конфиденциальности × категория данных + атрибуты**.

- **Уровень:** `Public` · `Internal` · `Confidential` · `Restricted` (спец. категория ПДн).
- **Категория:** `PII` · `PHI` (медицинские / спец. категория) · `FIN` · `EMPLOYEE`.
- **Атрибуты:** домен-владелец, правовое основание обработки, срок хранения (retention), разрешённые операции/среды.

### A.3 Каталог тегов
| Тег             | Уровень      | Примеры данных                          | Политика по умолчанию                                                                          |
|-----------------|--------------|-----------------------------------------|------------------------------------------------------------------------------------------------|
| `PII.Identity`  | Confidential | ФИО, дата рождения                      | шифрование; маскирование при отображении; доступ по роли                                       |
| `PII.Contact`   | Confidential | телефон, e-mail, адрес                  | шифрование/токенизация; маскирование                                                           |
| `PHI.Sensitive` | Restricted   | диагнозы, хрон. заболевания, заключения | усиленное шифрование; доступ только «врач»; обезличивание для аналитики; аудит каждого доступа |
| `PHI.LabResult` | Restricted   | результаты анализов                     | шифрование; RBAC «врач» + владелец-пациент; аудит                                              |
| `FIN.Payment`   | Confidential | платежи, реквизиты, договор             | шифрование/токенизация; маскирование; доступ «бухгалтерия»                                     |
| `EMPLOYEE.HR`   | Confidential | кадры, зарплата                         | шифрование; RBAC «HR»                                                                          |

### A.4 Где и как тегировать
- **На уровне поля (column-level)** в операционной БД (PostgreSQL): метки / `COMMENT` / политики безопасности на столбцах.
- **В каталоге данных** — единый реестр датасетов с тегами, владельцами и lineage.
- **В озере данных** — теги в метаданных при загрузке; распространяются на витрины BI/ML.

### A.5 Инструменты тегирования
| Задача                          | Инструмент                                                                            | Привязка к стеку компании                  |
|---------------------------------|---------------------------------------------------------------------------------------|--------------------------------------------|
| Каталог данных + lineage + теги | **Apache Atlas / DataHub / OpenMetadata** (open-source, разворачиваются в РФ-контуре) | интеграция с PostgreSQL, ClickHouse, Kafka |
| Маскирование/обезличивание в БД | расширение **anon (PostgreSQL Anonymizer)**                                           | поверх Postgres                            |
| Политики по тегам (ABAC)        | **Open Policy Agent (OPA)**                                                           | сервисы на Java в Kubernetes               |
| Управление ключами/токенами     | **HashiCorp Vault**                                                                   | Kubernetes                                 |
| Контроль исходящих данных       | **DLP**                                                                               | почта, выгрузки                            |

### A.6 Автоматизация на основе тегов
- **ABAC**: OPA принимает решение о доступе, читая теги данных и атрибуты пользователя.
- **Маскирование/обезличивание**: применяется автоматически по тегу при отдаче данных в нижние среды и аналитику.
- **Retention/удаление**: срок хранения и crypto-shredding запускаются по тегу.
- **Проверка релизов (целевое состояние)**: CI-проверка, что ни один сервис/контракт не отдаёт `Restricted`-данные наружу без маскирования; нарушение → блок релиза.
- **Алертинг**: доступ к `Restricted` и нетипичные обращения → события в мониторинг.

## Часть B. Инструменты, способы и меры по обеспечению конфиденциальности в потоках
Сгруппировано по слоям; в скобках — какие проблемы (P-xx из документа проблемных зон) закрывает.

| Слой                       | Меры и инструменты                                                                                                           | Этап потока              | Закрывает  |
|----------------------------|------------------------------------------------------------------------------------------------------------------------------|--------------------------|------------|
| Идентификация и доступ     | RBAC + ABAC через **OPA**, least privilege, MFA, каталог (AD/Keycloak)                                                       | процессы                 | P-04, P-06 |
| Шифрование                 | TLS везде; шифрование диска (LUKS/BitLocker); field-level шифрование спец. категории; ключи в **Vault/KMS**                  | хранение, передача       | P-02, P-03 |
| Маскирование/обезличивание | динамическое маскирование, **pg-anon**, токенизация (Vault transit), k-анонимность для BI                                    | использование, аналитика | P-09, P-13 |
| Каталог и происхождение    | **Atlas/DataHub** — классификация, теги, **Data Lineage**, реестр обработки (RoPA)                                           | сквозное                 | P-12, P-15 |
| DLP                        | контроль egress: почта, выгрузки аналитиков                                                                                  | передача                 | P-14, P-09 |
| Аудит и мониторинг         | логи доступа в **Elastic**; метрики/алерты в **Victoria Metrics**; аудит доступа к тегированным данным; обнаружение аномалий | процессы, сквозное       | P-05       |
| Сегментация сети           | контуры **мед / фин / общий**; mTLS между сервисами; **API gateway**                                                         | передача                 | P-06, P-03 |
| Безопасность API           | gateway; контракты скрывают спец. категории; object-level authz (пациент видит только своё); rate limiting                   | передача                 | P-04       |
| Жизненный цикл данных      | retention-политики; secure deletion / crypto-shredding; workflow «право на удаление» (152-ФЗ)                                | удаление                 | P-11       |
| Бэкап и резерв             | зашифрованные бэкапы; георезерв **в пределах РФ** (data residency)                                                           | хранение                 | P-10       |
| Governance приватности     | реестр обработки ПДн (RoPA), управление согласиями, минимизация форм сбора, DPIA                                             | сквозное                 | P-16, P-12 |

> Существующий стек компании (PostgreSQL, ClickHouse, Elastic, Kubernetes, Victoria Metrics, Java) покрывает большинство мер без новых классов ПО: Elastic — аудит, Victoria Metrics — алертинг, ClickHouse — обезличенный аналитический контур, Postgres + anon — операционное хранение с маскированием, Kubernetes + Vault — секреты и сегментация.
