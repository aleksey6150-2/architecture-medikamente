## 1. Назначение
Движок присваивает класс конфиденциальности данным **до пакетной загрузки** в аналитическое хранилище и раскладывает их по слоям с учётом Privacy by Design. Решает две заявленные сложности: входные структуры **меняются** (schema drift) и **не размечены** по классу конфиденциальности. Развивает аналитический контур из Task 2 и механизм тегирования из Task 1. Диаграмма — `c2_classification_engine.drawio`.

## 2. Конвейер движка (как работает)
1. **Приём (Ingestion) → Landing/Карантин.** Батч попадает в изолированный зашифрованный сырой слой. **По умолчанию данные считаются `Restricted`** (secure by default), пока не классифицированы.
2. **Профайлер схемы + детектор дрейфа.** Схема выводится «на чтение» (schema-on-read), профилируются типы, паттерны, кардинальность, доля пустых. Изменения схемы фиксируются в **Реестре схем** (версионирование). Новые/изменённые столбцы → на классификацию; неизвестное → в карантин.
3. **Движок классификации (ядро)** присваивает класс и **оценку уверенности**, комбинируя детекторы:
    - **Правила и словари** (`Сервис правил`): regex и справочники для известных PII (ИНН, СНИЛС, паспорт, телефон, e-mail), МКБ-коды и медицинская терминология → PHI, платёжные паттерны → FIN.
    - **ML** (`ML-сервис`): для неоднозначных столбцов — NER по свободному тексту (ФИО, адреса) и классификатор столбцов по профилю; модели версионируются в **Реестре моделей**.
    - Итог: класс (`Public/Internal/Confidential/Restricted`) + категория (`PII/PHI/FIN/…`) + уверенность.
4. **Карантин и ревью (human-in-the-loop).** Если уверенность ниже порога — данные/столбцы уходят в **Сервис ревью**, где стюард/DPO размечает их вручную. Разметка возвращается как обучающие примеры → **дообучение модели** (active learning).
5. **Обезличивание/маскирование** (`pg-anon`, токенизация Vault) применяется **по присвоенному классу** до записи в потребляемые слои.
6. **Контроль качества (quality gate)** проверяет покрытие классификацией и правила качества; провал → карантин.
7. **Загрузка по слоям** хранилища (раздел 4).

### Обработка дрейфа схемы и неразмеченности (явно)
- **Дрейф:** конвейер **метаданно-управляемый**, схема не захардкожена; новые столбцы автоматически профилируются и классифицируются, изменения версионируются, неизвестное — в карантин (не теряется и не «протекает» неклассифицированным).
- **Неразмеченность:** классы присваивает сам движок (правила + ML); до присвоения — режим `Restricted by default`; спорное — на ручную разметку. Так ни одно поле не попадает в открытые слои без класса.

## 3. Теги и каталог
Присвоенные классы/теги пишутся в **Каталог данных** (DataHub/Atlas) вместе с **Data Lineage**, тег наследуется производными наборами вниз по конвейеру и **управляет политиками** (ABAC, маскирование, retention) во всех слоях.

## 4. Слои хранилища и дополнительные меры
Medallion-архитектура: чувствительность снижается от слоя к слою, а конфиденциальные данные, которые **должны** храниться в идентифицируемом виде, изолируются в отдельном Restricted-слое.

| Слой                   | Содержимое                                                                              | Доступ / защита                                                                 |
|------------------------|-----------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| **Landing / Карантин** | сырые непроверенные данные; `Restricted by default`; неклассифицированное               | только конвейер + DPO; шифрование; изоляция                                     |
| **Bronze**             | сырые **с тегами классификации**                                                        | ограниченный доступ по ABAC                                                     |
| **Silver**             | очищенные, конформные, **PII/PHI обезличены/маскированы** по тегам                      | основной аналитический слой; широкий внутренний доступ по ABAC                  |
| **Gold**               | агрегаты и **анонимизированные витрины** (k-анонимность)                                | самый низкий уровень риска; широкий доступ; DLP на выгрузках                    |
| **Restricted-слой**    | конфиденциальные данные, нужные идентифицируемыми (напр., продольные мед. исследования) | **field-level шифрование**, строгий ABAC, полный аудит, отдельно от общих слоёв |

**Кроме слоёв — другие меры:**
- **Tag-driven ABAC** (OPA) на каждом слое — доступ зависит от тегов данных и атрибутов пользователя.
- **Field-level шифрование / токенизация** (Vault) для конфиденциальных полей даже внутри слоёв.
- **Динамическое маскирование** при запросах (`pg-anon`) для ролей без права видеть сырое.
- **Lineage** — классификация у источника распространяется на все производные наборы.
- **Аудит** доступа к Restricted; **DLP** на экспортах из Gold; проверка **реидентификации** (k-аноним.) перед промоушеном в Gold.
- **Периодическая переклассификация** при улучшении модели и изменении схемы.

## 5. Метрики эффективности классификации
| Метрика                                                        | Зачем                                                                                                    |
|----------------------------------------------------------------|----------------------------------------------------------------------------------------------------------|
| **Recall / FNR по чувствительным классам (PII/PHI)**           | главное: пропуск конфиденциального поля — самая дорогая ошибка; целимся в высокий recall на `Restricted` |
| **Precision / F1 по классам, матрица ошибок**                  | баланс ложных срабатываний и пропусков                                                                   |
| **Покрытие автоклассификации** (% полей без ручного ревью)     | операционная эффективность, стоимость                                                                    |
| **Доля карантина / уверенность ниже порога**                   | объём ручной работы и backlog ревью                                                                      |
| **Частота дрейфа схемы / новых неклассифицированных столбцов** | устойчивость к структурным изменениям                                                                    |
| **Throughput и время классификации батча**                     | производительность конвейера                                                                             |
| **Уровень k-анонимности витрин Gold**                          | риск реидентификации                                                                                     |
| **Деградация качества модели во времени**                      | мониторинг и потребность в переобучении                                                                  |

**Как метрики помогают оптимизации.** Высокий FNR по PHI → ужесточить правила, понизить порог для чувствительных классов, дообучить модель. Высокая доля карантина → добавить паттерны/словари и улучшить модель → меньше ручного труда и выше скорость. Узкое место по throughput → масштабировать воркеры/партиционирование. Ручные правки из ревью становятся **размеченными данными для дообучения** — замкнутая петля улучшения precision/recall (active learning).

## 6. Масштабируемость и расширение
- **Горизонтальное масштабирование движка:** распределённая обработка (Spark / партиционированные воркеры) на **Kubernetes**, параллелизм по файлам/партициям/таблицам; **stateless**-воркеры с автоскейлингом (HPA) по объёму батча.
- **Развязка этапов** через оркестратор (Airflow/Argo) и очереди — этапы масштабируются независимо; при необходимости переход с пакетной обработки на микробатч/стриминг **без смены архитектуры**.
- **ML-инференс** масштабируется отдельным сервисом (батч-скоринг, реплики).
- **Хранилище:** ClickHouse с **шардированием и партиционированием**, колоночное хранение, **тиринг** (hot/cold), дешёвое объектное хранилище для сырого слоя.
- **Рост числа пользователей:** ABAC + слои означают, что добавление ролей/пользователей не меняет конвейер; масштабируются реплики чтения и конкурентность запросов, BI получает отдельные вычислительные ресурсы.
- **Каталог и реестры** (схем, моделей) масштабируются как метаданные-хранилища.

> Принцип: движок — метаданно-управляемый и stateless, поэтому растёт горизонтально; хранилище отделяет сырое (дёшево, объектно) от аналитического (ClickHouse, шардируется), а доступ управляется тегами, а не жёсткой схемой.
