# Task 4 — анализ рисков снижения производительности

Отчёт: оценка узких мест при миграции монолита на микросервисы

## 1. Анализ ситуации
**Как есть.** Учёт ведётся на файлах: журналы записи и список пациентов в Excel, медкарты и анализы — файлы в папках на общем диске, финансы — две системы 1С в **файловом режиме** (Бухгалтерия и Торговля-склад, связаны через OLE), касса — ККМ по TCP/IP-OLE. Всё работает на **единственном on-prem сервере** Windows Server в офисе. IT-команда — **3 человека**.

**Цели миграции.** Перейти на единую современную (микросервисную) архитектуру: порталы клиента и ресепшена, платёжный шлюз, CRM, интеграция с лабораторией по API, озеро данных для BI/ML. Заложен рост клиентской базы **×5** и открытие **филиалов**, мобильное приложение и самозапись.

При таком переходе риски — не только функциональные, но и **производительностные**: распределённая система добавляет сетевые задержки, накладные расходы на сериализацию и согласованность данных, новые точки отказа. Ниже они структурированы по диаграмме Исикавы.

## 2. Ключевые процессы и компоненты, затрагиваемые миграцией
- **Базы данных:** перенос из Excel/файлов и 1С в доменные БД (PostgreSQL); распределение данных по сервисам, согласованность, объёмы.
- **Коммуникационные каналы:** межсервисное взаимодействие (синхронное/асинхронное), внешние интеграции (лаборатория, банк, ККМ, 1С), каналы между филиалами.
- **Серверное оборудование:** уход от единого сервера к кластеру (Kubernetes), резервирование, ресурсы, сеть.
- **Бизнес-логика:** декомпозиция монолитной логики на сервисы, границы доменов, перенос легаси-правил.

## 3. Диаграмма Исикавы — категории и причины
Диаграмма:  Эффект (голова рыбы): **снижение производительности нового решения после миграции**. Шесть категорий причин:

![ishikawa.drawio.png](Task4/img/ishikawa.drawio.png)

| Категория                         | Потенциальные причины узких мест                                                                                                                                               | Чем грозит производительности                                              |
|-----------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------|
| **Инфраструктура и оборудование** | единый on-prem сервер без масштабирования; единая точка отказа, нет резерва; задержки каналов между филиалами; нехватка ресурсов под Kubernetes; нет автоскейлинга под рост ×5 | нехватка мощности под пиковую нагрузку, простои, рост latency для филиалов |
| **Данные и базы данных**          | 1С в файловом режиме (блокировки); грязные данные из Excel; распределённые транзакции и рассинхрон; отсутствие индексов и N+1 запросы; рост объёмов без шардинга               | медленные запросы, блокировки, деградация при росте данных                 |
| **ПО / Архитектура**              | неверные границы сервисов; «распределённый монолит»; синхронные цепочки вызовов; отсутствие кэширования; нет таймаутов/circuit breaker                                         | сложение задержек, каскадные сбои, повторная нагрузка на БД                |
| **Интеграция и коммуникации**     | chatty-вызовы без async/очередей; легаси-интеграции по OLE (1С, ККМ); задержки внешнего API лаборатории; API Gateway как узкое место; нет backpressure/rate limiting           | сетевые задержки, заторы на шлюзе, зависимость от внешних систем           |
| **Процессы и методология**        | big-bang вместо постепенной миграции; нет нагрузочного тестирования; нет baseline-метрик; нет distributed tracing/наблюдаемости; нет плана отката                              | проблемы выявляются поздно, в проде, без возможности быстро откатиться     |
| **Персонал и компетенции**        | малая команда (3 IT) на большой объём; дефицит опыта в микросервисах/K8s; bus factor; сопротивление пользователей; слабое обучение                                             | ошибки проектирования, медленная реакция, перегрузка поддержки             |

## 5. Логика приоритизации
**P0** — то, без чего миграцию нельзя начинать безопасно: способ перехода (Strangler), измеримость (baseline + нагрузочное тестирование + наблюдаемость), возможность отката, чистота переносимых данных, правильные границы сервисов и масштабируемая инфраструктура. Без них узкие места выявятся уже в проде и без возможности быстро отступить.

**P1** — устранение конкретных источников задержек и отказов: async-взаимодействие и кэш, паттерны устойчивости, изоляция легаси, оптимизация БД, CI/CD и компетенции.

**P2** — организационные меры с отложенным эффектом на производительность (обучение, управление изменениями).

> Системный вывод: наибольший риск производительности при этой миграции дают **сочетание распределённости и легаси-данных** (синхронные цепочки + 1С в файловом режиме + рассинхрон) на фоне **слабой наблюдаемости и малой команды**. Поэтому приоритет отдаётся не отдельным оптимизациям, а измеримости, постепенности и обратимости перехода.
